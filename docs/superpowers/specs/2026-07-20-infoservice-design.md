# InfoService: Telegram-сервис персональных информационных отчётов

## 1. Цель и границы первой версии

InfoService — публичный self-hosted Telegram-бот на базе MIT-проекта Horizon. Пользователь подключает собственный ключ DeepSeek, создаёт несколько независимых отчётов, добавляет источники и правила, выбирает расписание и получает готовые сводки в личный чат с ботом.

Первая версия управляется только командами и inline-кнопками Telegram. Настройка естественным языком, платежи и использование общего платного LLM-ключа не реализуются. В схеме данных сохраняется источник учётных данных `byok`/`platform`, но пользовательский интерфейс разрешает только `byok`; `platform` остаётся выключенной заготовкой для будущего тарифа.

Публичный продукт называется **InfoService** и публикуется как fork `Thysrael/Horizon` в `AntonL9vov/InfoService`. Исходная MIT-лицензия, copyright и ссылка на Horizon сохраняются. Ядро Horizon остаётся отдельно от Telegram- и многопользовательского слоя, чтобы было проще переносить обновления upstream.

## 2. Пользовательский сценарий и интерфейс Telegram

### Онбординг

1. `/start` создаёт пользователя по неизменяемому `telegram_user_id`, запоминает личный `chat_id` и предлагает выбрать часовой пояс.
2. Бот предлагает добавить DeepSeek API key в личном чате. Полученное сообщение с ключом удаляется после обработки, ключ проверяется коротким запросом к API, шифруется и сохраняется. В дальнейшем показывается только маска ключа.
3. Пользователь попадает в главное меню: **Отчёты**, **LLM**, **Настройки**, **Помощь**.

Групповые чаты в v1 не поддерживаются: бот отвечает подсказкой перейти в личный чат. Интерфейс по умолчанию русский; тексты хранятся в отдельном каталоге сообщений, чтобы позже добавить английский без изменения обработчиков.

### Управление отчётами

Пользователь может создать до пяти отчётов. Мастер создания последовательно запрашивает название, источники, правила, расписание и подтверждение. Каждый шаг можно отменить; незавершённое состояние мастера хранится в FSM и не создаёт частичных сущностей в БД.

Для каждого отчёта доступны действия:

- включить, приостановить, изменить или удалить;
- управлять источниками;
- задать порог AI-оценки от 0 до 10, категории, исключаемые темы, лимит итоговых материалов от 1 до 30 и пользовательскую инструкцию до 2 000 символов;
- выбрать язык итогового отчёта;
- настроить готовое расписание либо cron;
- запустить вручную;
- посмотреть последние 20 запусков и повторить отправку готового результата.

Готовые расписания: ежедневно, по будням и еженедельно с выбранными временем и днём недели. Расширенный режим принимает стандартное пятичастное cron-выражение. Минимальная частота — один запуск в час. Расписание интерпретируется в часовом поясе отчёта; по умолчанию используется часовой пояс пользователя.

### Доставка результата

Отчёт отправляется в личный чат владельца. Telegram-рендерер использует HTML-разметку, экранирует недоверенный текст и делит результат на смысловые части не длиннее 3 800 символов. Первое сообщение содержит название, период, число просмотренных и выбранных материалов. Каждый материал содержит оценку, краткое резюме и ссылку. Если полный результат слишком велик, бот дополнительно отправляет UTF-8 Markdown-файл.

При частичном отказе источников пользователь получает отчёт и короткое предупреждение. При полном отказе источников, неверном LLM-ключе или ошибке DeepSeek отправляется понятное сообщение без секретов и внутренних traceback.

## 3. Архитектура и данные

### Процессы

Docker Compose запускает три сервиса и PostgreSQL:

- `bot` — aiogram 3.25 long polling, команды, callback-запросы и FSM;
- `worker` — выбирает готовые к запуску задания, вызывает Horizon и доставляет результат;
- `scheduler` — каждые 30 секунд создаёт задания для наступивших расписаний;
- `postgres` — постоянные настройки, зашифрованные секреты и история запусков.

Redis и отдельная очередь в v1 не нужны. Планировщик атомарно захватывает наступившие отчёты транзакцией PostgreSQL через `SELECT ... FOR UPDATE SKIP LOCKED`, обновляет `next_run_at` и создаёт запись запуска. Уникальность `(report_id, scheduled_for)` защищает от повторного задания. Worker аналогично захватывает ожидающий запуск; зависший `running` после рестарта переводится обратно в очередь только один раз после таймаута.

По умолчанию одновременно выполняются не более двух запусков всего сервиса и не более одного запуска на пользователя. Повторный ручной запуск уже работающего отчёта отклоняется. Эти значения задаются переменными окружения.

### Схема данных

- `users`: UUID, `telegram_user_id` и `chat_id` с unique-ограничениями, язык, часовой пояс, timestamps.
- `llm_credentials`: владелец, provider, `credential_source`, модель, необязательный base URL, ciphertext, маска ключа, статус последней проверки и timestamps. В v1 у пользователя одна активная DeepSeek credential.
- `reports`: владелец, имя, enabled, язык, lookback, AI-порог, лимит материалов, категории/исключения, пользовательская инструкция, тип расписания, cron, часовой пояс, `next_run_at`, timestamps.
- `sources`: отчёт, тип, отображаемое имя, enabled и валидированный JSONB-конфиг конкретного адаптера.
- `report_runs`: отчёт, причина `scheduled`/`manual`, `scheduled_for`, статусы `queued`/`running`/`succeeded`/`partial`/`failed`, счётчики, итоговый Markdown, безопасная сводка ошибки и timestamps.
- `source_run_results`: запуск, источник, статус, число материалов и безопасная ошибка для диагностики.

Все запросы репозиториев, кроме системного планировщика, требуют `user_id`. Объект отчёта или запуска никогда не загружается только по UUID без проверки владельца. Итоги и диагностика хранятся 30 дней; scheduler ежедневно удаляет более старые записи. Исходные тексты материалов после завершения запуска в БД не сохраняются.

SQLAlchemy 2 async используется для доступа к PostgreSQL, Alembic — для версионируемых миграций. Миграции выполняются отдельной командой перед запуском сервисов, а не автоматически каждым процессом.

### Адаптер Horizon

Новый внутренний интерфейс `ReportExecutor.execute(request) -> ReportExecutionResult` принимает полностью собранную конфигурацию отчёта и уже расшифрованную credential только на время вызова. Он преобразует записи БД в существующие Pydantic-конфиги Horizon, использует scrapers, дедупликацию, анализ, фильтрацию, enrichment и summarizer, но не пишет GitHub Pages и не вызывает текущие email/webhook-доставщики.

Клиенты LLM изменяются так, чтобы принимать секрет напрямую через объект runtime credential. Пользовательские ключи нельзя помещать в `os.environ`, потому что параллельные задания разных пользователей работают в одном процессе. Старый CLI Horizon продолжает поддерживать env-based credentials для обратной совместимости.

Пользовательская инструкция добавляется только в ограниченный раздел правил оценки и сводки. Системный prompt явно объявляет содержимое источников недоверенными данными. Результаты AI валидируются существующей моделью и не получают доступа к ключам, БД или инструментам.

### Источники

Стабильными в v1 считаются RSS/Atom, публичные Telegram-каналы, Hacker News и GitHub releases/user events. Также в интерфейсе доступны текущие адаптеры Horizon для Reddit, Google News, GDELT и OSSInsight с пометкой **beta**.

Twitter/X и OpenBB являются опциональными адаптерами: бот показывает их только когда оператор включил соответствующую capability. Twitter требует серверного Apify token либо Playwright cookies; OpenBB требует дополнительного набора зависимостей. Отсутствующая capability не ломает отчёт и объясняется пользователю до сохранения источника.

Конфигурация каждого типа проверяется отдельной Pydantic-моделью до записи JSONB. URL проходят существующую SSRF-защиту Horizon. Telegram принимает только username публичного канала, без приватных каналов и пользовательских сессий.

## 4. Безопасность, лимиты и эксплуатация

API-ключи шифруются authenticated encryption с серверным `APP_ENCRYPTION_KEY`. Ключ шифрования, Telegram token, БД-пароль и серверные credentials источников передаются только через environment/secrets и никогда не попадают в Git. Логи проходят централизованную редактировку секретов; тело пользовательского ключа и полный ответ LLM не логируются.

Ограничения одного пользователя в v1:

- 5 отчётов;
- 30 источников на отчёт;
- один запуск отчёта в час;
- один выполняющийся запуск;
- до 30 материалов в результате;
- пользовательская инструкция до 2 000 символов;
- история за 30 дней.

Все callback-data содержат короткий тип действия и UUID, но обработчик повторно проверяет владельца. Ошибки Telegram 429 повторяются с `retry_after`; временные сетевые и LLM-ошибки повторяются до трёх раз с экспоненциальной задержкой. Ошибки авторизации и валидации не повторяются. Метрики v1 выводятся структурированными логами: длительность запуска, число материалов, токены, статус каждого источника и доставки; секреты и содержимое материалов исключены.

Будущий платный режим добавится через реализацию `PlatformCredentialProvider`, feature flag и квоты. Таблицы платежей, тарифы и checkout в v1 намеренно отсутствуют.

## 5. Проверка и критерии готовности

### Автоматические тесты

- Unit: валидация каждого source-конфига, cron и часовых поясов; вычисление `next_run_at`, включая DST; лимиты; шифрование/расшифрование и редактирование секретов; разбиение и экранирование Telegram-сообщений; пользовательская инструкция не меняет системные границы prompt.
- Repository/integration с PostgreSQL: изоляция пользователей, каскадное удаление, уникальность scheduled runs, конкурентный захват через `SKIP LOCKED`, восстановление зависших заданий и retention.
- Bot handlers: онбординг, добавление/замена/удаление ключа, мастер отчёта, отмена FSM, CRUD источников, ручной запуск, запрет доступа к чужому UUID и обработка группового чата.
- Horizon adapter: успешный отчёт, пустой набор, частичный отказ, полный отказ, неверный ключ, таймаут и пользовательский prompt; внешние HTTP/LLM-вызовы заменяются mock/respx.
- Delivery: короткий и многочастный отчёт, fallback-файл, Markdown/HTML-инъекции, Telegram 429 и permanent failure.
- Regression: существующий набор тестов Horizon продолжает проходить; прежние CLI-команды сохраняются.

### Приёмочные сценарии

1. Новый пользователь в личном чате добавляет валидный DeepSeek key, создаёт RSS-отчёт на 09:00 в своём часовом поясе и получает его автоматически.
2. Тот же пользователь создаёт второй GitHub-отчёт с cron и собственным prompt; настройки и история отчётов не смешиваются.
3. Другой Telegram-пользователь не может увидеть, изменить, запустить или повторно отправить чужой отчёт даже с известным UUID.
4. Один источник падает, но остальные формируют отчёт со статусом `partial`; при полном отказе пользователь получает безопасное уведомление.
5. Перезапуск scheduler/worker не создаёт дубликат и не теряет уже запланированный запуск.
6. В БД, логах, Telegram-ответах и tracebacks нет открытого LLM-ключа.
7. Чистый сервер поднимает проект через документированные Docker Compose-команды после заполнения `.env`; миграции применяются, healthchecks проходят.

Готовность v1 означает прохождение этих сценариев, обновлённые русский README и английское краткое описание, `.env.example` без секретов, Docker Compose, инструкции BotFather/DeepSeek и явную таблицу стабильных и beta-источников.
